## Context

Hara v1.1 ship 후 사용자 지시 (2026-05-27): "이제 다시 알아서 진행해 ... 백그라운드 세션 부르는 방식으로 테스트 및 하니스 개선". 본인 (Claude root coordinator)가 starpin-fleet 프로젝트로 *real-world Fleet dogfood* 진행 — 4 children parallel spawn (Agent run_in_background) + inter-child consume + 4 cross-cutting invariants.

## Review focus

### 1. v1.2 §14.8 (lock & invariant enforcement) 강도

- single-method consume의 grep 기반 enforcement가 *실제* enforcement인가, 아니면 *self-discipline 보조*인가?
- `lock-grep-gate` skill의 grep pattern (`^import \{[^}]*\} from '\.\./(<provider>)/index\.js'`)이 *간접 호출* (helper fn re-export 등) 못 잡음 — false negative risk
- invariant-guard marker `// @invariant-guard: <util>` 패턴 — child가 marker만 달고 *호출 안 함* 가능 (또 false positive 피하기)

### 2. §14.9 inter-child consume timing 3 option

- (a) lock-spec stub — `throw new Error('not-implemented')` 패턴이 *consumer test*에 어떻게 영향? consumer는 unit test에서 mock 못 하는데 stub은 throw — test 시 어떻게?
- (b) type-only ambient — `<provider>.d.ts` 작성 시 consumer worktree에만 두는데, 본 worktree에 commit하면 parent merge phase에 *어떻게 제거되는지* 명세 부재
- (c) topological spawn — parent가 sequential dispatch한다는데 *spawn skill이 이를 어떻게 강제*? 본 v1.2 patch는 ADR field만 추가 — 실제 dispatch logic은?

### 3. §14.10 scope-bounded gates

- spawn-subtree-prompts skill이 *child별 tsconfig.<child>.json* 생성한다는데 — `npm install`은 root level, child별 dependency 격리 가능?
- scope-only typecheck가 *shared transitive imports*를 어떻게 포함시키는지 자동? 본 v1.2는 명령 inline에 src/shared/*.ts 손으로 추가 — fragile

### 4. F80 user-delegated approval 경로 안전성

- `delegation_source` field가 *quoted user message*인데 — *과거 메시지 인용*으로 위조 가능 (autonomous 세션이 사용자 동의 없이 거짓 delegation 주장)
- 본 v1.2 patch에 *delegation source 유효성 검증* 부재 — claude가 user 메시지 *재구성* 가능
- HC-7/8/9 영향 우회 risk?

### 5. LOCKED-INTERFACE template 신설 적용성

- 기존 fleet-mini/starpin-fleet의 locked-interface는 본 신규 양식 미적용 — 후속 dogfood에서 retroactive 적용 필요?
- 신규 template의 *defensive validation policy* 섹션 — 모든 branded type method가 *trust* vs *re-validate* 선택 의무라는데, *기준 heuristic* 없음

### 6. starpin-fleet dogfood의 evidence 무결성

- F71 (v1.1 codex finding)의 fleet-mini 데모트 패턴과 일치 — 본 starpin-fleet도 같은 worktree, real git worktree 생략. F92 (= F70-fleet-2)로 명시 — 본 v1.2 ship evidence로 *충분*한가?
- 11 finding 도출 — *추가 round*에서 5+ 더 발견 가능성 있을 텐데, v1.2 ship으로 closure?
- ADR-011의 "lock enforcement가 typecheck 수준에 근접" 주장 — grep 기반이라 *근접*은 맞지만 *equivalent* 아님

### 7. cleanup pass 부재 (v1.2)

- 사용자 원칙 "obsolete 적극 제거" — v1.2 amendment는 새 규칙 추가가 본질. *제거할 obsolete*가 v1.2에 있는가? (예: v1.0 시기의 보존된 historical context 중 v1.2가 superseded 처리 가능한 것)

### 8. real-world wall-time benefit 검증 미진행

- starpin-fleet은 ~500 LOC — 의도된 한계로 wall-time 측정 안 함
- *언제* 측정 dogfood 진행할지 v1.2에 roadmap 부재

## Review format

REVIEW 양식 (`templates/REVIEW.template.md` 참조):
- finding별 `severity` (blocker / major / minor / nit / info)
- `위치` (파일:라인)
- `근거`
- `제안`

특히:
- **blocker / major** finding은 v1.2 ship 전 의무 처리
- **minor / nit / info**는 carry-over OK (v1.3 후보)
- HC-7/8/9 우회 가능성 (특히 F80 delegation_source 위조) 보이면 자동 blocker

- v1.3 후보 (F70-fleet-1/2/3, F86)는 *언급*만, finding으로 발행 안 해도 OK
