## Part B — New surface findings

### Finding 68: Local capability approval fields do not enforce user-only activation
- severity: major
- target: templates/LOCAL-SKILL.template.md:6-11, templates/LOCAL-ROLE.template.md:6-11, templates/CAPABILITY-MANIFEST.template.md:8-13
- detail: HARNESS §13.5 requires user approval for local capability activation in all modes, but the local templates expose generic `approval.approver: <pending>` and `mode: <strict | balanced | autonomous>` without saying `approver` must be `user` for `status: approved` or manifest Active entries. Because HARNESS §4.3 allows `codex-review`, `claude-reviewer`, and `claude-self-test` approvers for other artifact types, a fresh project author can accidentally mark a local skill approved by Codex review alone and move it to Active.
- suggested_action: In all three adaptive templates, add an invariant near front-matter: `status: approved` and any Active manifest entry require `approval.approver: user`; Codex review is evidence only, not approval. Add a review-local-layer checklist item that flags non-user local activation as blocker.
- references: HARNESS.md:397; HARNESS.md:340; templates/LOCAL-SKILL.template.md:7-11; templates/CAPABILITY-MANIFEST.template.md:36-43

### Finding 69: Blueprint and review procedures do not require Active local capabilities as inputs
- severity: major
- target: phases/01-blueprint.md:5-21; skills/plan-blueprint.md:13-44; skills/request-codex-review.md:13-47
- detail: v0.6 says Blueprint should use base + local layer, but Phase 01 inputs list only intake/config, and plan-blueprint/request-codex-review do not require `.harness/capabilities.md` or the Active skill/role files in the Blueprint drafting or Codex prompt. A session may have loaded local capabilities, but the non-interactive `codex-exec-review.sh` prompt can still review only `.harness/docs/blueprint.md`, missing the local spec-first or domain-safety rules.
- suggested_action: Add `.harness/capabilities.md` and all Active paths to Phase 01/02 inputs and to request-codex-review preflight. For text reviews, require prompt files to include a “Local capability context” section or explicitly state “manifest Active empty by decision.”
- references: HARNESS.md:352-356; phases/01-blueprint.md:7-9; skills/plan-blueprint.md:15-17; skills/request-codex-review.md:38-47

### Finding 70: Phase 00 still tells authors to create new base project-types for deep templates
- severity: major
- target: phases/00-intake.md:20
- detail: Activity 2 still says that if a future deep template is needed, creating a new project-type is itself harness work. That is the old v0.5 path and conflicts with v0.6’s default path: `_generic` + Local Capability Synthesis first, promotion only after evidence. This is exactly where a project author decides between §13.5 synthesize and §6 harness-amend, so the ambiguity is operational, not cosmetic.
- suggested_action: Replace the sentence with: “매칭 없거나 seed가 얕으면 `_generic`으로 시작하고 Local Capability Synthesis로 프로젝트 로컬 skill/role/checklist를 만든다. 새 base project-type은 HARNESS §13.6 promotion 기준 충족 후에만 §6 절차로 추가한다.”
- references: phases/00-intake.md:20; project-types/README.md; HARNESS.md:401-409

### Finding 71: resume-session treats capabilities.md as unconditional in self-build contexts
- severity: minor
- target: skills/resume-session.md:23-30
- detail: CLAUDE.md and AGENTS.md correctly qualify manifest loading as “project context,” and HARNESS §13.3 says read it if it exists. resume-session instead lists `.harness/capabilities.md` unconditionally. The harness self-build already has a `.harness/` directory for reviews/config but no capability manifest, so a fresh Claude session can misread a missing manifest as an error.
- suggested_action: Change step 1.5 to “if `.harness/capabilities.md` exists, read it; if absent in self-build, record Active local capabilities = none.” Keep missing manifest as a Phase 00 violation only for generated projects after bootstrap.
- references: CLAUDE.md:11-13; AGENTS.md:11; HARNESS.md:352-354; skills/resume-session.md:28

### Finding 72: new-project manifest substitution leaves visible template placeholders
- severity: minor
- target: scripts/new-project.sh:109-112; templates/CAPABILITY-MANIFEST.template.md:6,19
- detail: Smoke test in `/private/tmp` produced a syntactically readable `.harness/capabilities.md`, but it still contains `date: <YYYY-MM-DD>` and heading ``# `<project name>` — Capability Manifest`` after bootstrap. The manifest can function as a draft, but it is not immediately clean or approval-ready, and the title contradicts the already substituted `project_name` front-matter.
- suggested_action: Have new-project.sh substitute date and `<project name>` as well, or make those placeholders intentionally absent from the seed manifest. Keep `status: draft` and pending approval until Phase 00 synthesis/user approval completes.
- references: scripts/new-project.sh:109-112; templates/CAPABILITY-MANIFEST.template.md:6,19
